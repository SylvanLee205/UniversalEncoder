# iPhone 录屏批量归档压缩 —— 项目总结

> 一句话：用 Intel Arc A380 的 QSV 硬编做 HEVC/ICQ 归档，**画质导向 + 2.5 Mbps 天花板**，
> 实测平均省 **86.8%** 体积，肉眼几乎看不出损失。定稿程序 `UniversalEncoder_v37.py`。

---

## 一、最终参数（定稿 v37）

| 项 | 值 | 为什么 |
|---|---|---|
| 编码器 | `hevc_qsv` + **ICQ**（`-global_quality:v`） | 同码率优于 CQP；比 VBR 硬封好得多 |
| 质量 | **Q32** | 1080p NEG≈84 / 720p NEG≈80；再低一档只换 ~1 分却多花 8~17% 体积 |
| 上限 | **2500 kbps**（超了自动抬 Q，容差 1.08） | 只对 1290p60/2K/4K 这类生效；接管件实测均值 2.46M = 98.5% ✓ |
| preset | **medium**（QSV）/ **p5**（NVENC） | medium 与 veryslow 实测几乎同画质（621/85.90 vs 629/85.92），但快 1.44 倍 |
| 音频 | `libopus 64k` VBR（实际约 56k） | 两套独立实测一致：单声道只省 6~9%，不值；40k 只省文件 0.7~4.5% |
| 并发 | **2 路** | 吞吐拐点；菜单【10】可切实测/手动 |
| GOP | 8 秒 | 1080p@22 → 176；配合硬解零拷贝 |
| 解码 | QSV 零拷贝 → 回退 d3d11va → CPU | 避免 v2 时代"CPU 解码 0.几倍速" |
| Q 缓存 | **关闭** | 会把简单文件按同规格最难文件的 Q 压缩，白丢 3~8 档画质 |
| 启动 | 一次 ffmpeg 探测 + 缓存 + 编码器列表判平台 | **0.1 秒**（原 4.9 秒） |

## 二、怎么用

1. 把视频放到脚本所在目录（或其子目录）；
2. 运行 `UniversalEncoder_v37.py`；
3. **菜单一路默认即可**：Q32 / 2.5 Mbps / 音频 64k / 安全模式 output/ / 【9】默认档位 / 【10】默认 2 路；
4. 跑完看 `_encode_run.log`：每行含体积变化、**视频码率、Q、耗时**；失败会写原因，单文件最多重试 3 次。

**建议别选**：【9】的「现场实测」（简单素材上会挑最慢的 veryslow，实测出过 VMAF 19.88 这种垃圾值）。

## 三、真实批次实测（16 个 iPhone 录屏，2 并发）

| 指标 | 结果 |
|---|---|
| 成功 / 失败 | **16 / 0** |
| 平均体积 | 310 MB → **约 41 MB（−86.8%）**，无一个变大 |
| Q 分布 | Q32 ×12；Q33/Q35/Q38/Q40 各 1（真超标或临界） |
| 上限接管件落点 | 2.62 / 2.50 / 2.40 / 2.33 Mb/s → 均值 **2.46 = 上限 98.5%** |
| 重压次数 | 4 次（每文件 ≤1 次） |
| 用时 | 5 分 46 秒（16 文件） |
| 启动 | 0.1 秒 |

> 关掉 Q 缓存前后对比（同 16 文件）：0.56M/Q40 → **1.46M/Q32**、1.15M/Q40 → **2.50M/Q33**
> 等 5 个文件画质明显提升，代价是总体积多 1.8 个点、多 2 遍重压（+33 秒）。

## 四、关键实测结论（踩过的坑都在这）

1. **源码率 ≠ 内容难度**。同样 Q32：静态 UI/文字页只出 0.56~1.5 Mbps，屏内视频/游戏/噪点出 2.5~6 Mbps。
   源码率 15 Mbps 只是对方编码器的选择，不代表信息量。
2. **同一个 Q 数字在不同版本含义不同**：CQP(`-q:v`) 与 ICQ(`-global_quality:v`) 差别巨大
   （1080p Q32：352 kbps/78.3 vs 621 kbps/85.9）。**ICQ 相对 CQP 的同码率优势只有约 +0.6 分**；
   之前说的 +4.9 分是 ICQ 对比「VBR 硬封」，别记混。
3. **AV1 硬件不要碰**：Intel QSV 上 `-q:v 30` 对 av1_qsv 是 0~255 的 QP 刻度（≈近无损），
   实测把 16998 kbps 压成 4706 kbps→换成 `-global_quality:v` 才正常。AV1 只在 <0.005 bpp 时才赢 HEVC。
4. **降规格不划算**：1080p30 Q32 与原生 1290p60 Q37 相比，同码率低 4.8 分；省 44% 体积要付 12 分。
   录屏里 UI/弹幕是**原生分辨率细节**，降分辨率直接糊字；降帧率在 UI 上会卡（30→20fps 就掉 2.5 分）。
5. **画质是导向，体积是天花板**：绝不为"花满预算"降 Q（那会把上限变成目标、体积上涨且画质不可比）。
6. **Q 是整数、一格 7~13% 码率** → 落点只能在 2.3~2.7 的带里，这是可预测性的物理边界。
7. **启动慢的根因**：脚本启动要 spawn 3 次 ffmpeg（-version ×2、-encoders），ffmpeg.exe 有 165MB，
   Windows 每次都要过安全扫描 → 合并成 1 次 + 缓存 + 用编码器列表判平台 = 0.1 秒。
8. **VMAF 要看方法**：同一文件同一 preset，单段抽帧与全片多窗口能差 4~6 分（1080p Q32：85.9 vs 79.6）。
   NEG 模型比默认低约 2.1 分。**绝对值只在自己那套方法内可比**。

## 五、工程经验（血泪）

- **最大收益只有三件**：①修 ICQ（AV1 膨胀）②上限改成反解调 Q（不是 VBR 硬封）③启动提速。
  其余十几版大多是界面文案与版本折腾 —— **功能应当尽早冻结**。
- **凭记忆写锚点必翻车**：本项目我自己制造了 6 个 bug（垃圾标定覆盖 medium、上限菜单显示与取值错位、
  编码器解析写错、两次缩进把文件写坏、容差常量记错、grep 输出拼锚点漏行）。
  **规矩：改函数内部先读原文；用行号定位；改完立刻编译 + 实跑一遍。**
- **补丁要打在对的地方**：前几版「平台判断」补丁误打到 `benchmark_concurrency()` 里的同名调用，
  真正运行的 `main()` 那处没改 → 三版都没生效。
- **缓存类功能要防污染**：Q 缓存/标定缓存都出现过「垃圾结果被缓存并跨分辨率复用」，
  已加可信度检查（VMAF<50 视为无效）与开关。
- **测量要留证据**：所有结论都写进 `编码参数与问题总结.md`（21 章），下次不用重新试。

## 七、遗留事项

1. **NVIDIA 需在 N 机验证**：上限模式已改为 QVBR（`-b:v <上限> + -maxrate/-bufsize`，一遍完成，不做反解），
   在 `build_ffmpeg_command` 约 3292 行。要确认：①是否咬住 ~2500 kbps；②与 `-cq` 同用画质是否变差
   （不对就把该行改回 `-b:v 0`）。
2. N 卡可用 `-rc-lookahead` / `-lookahead_level`（安全，QSV 上它配 `-b:v` 会崩），本机无卡未加。
3. 菜单【9】【10】的「现场实测」分支未验证。
4. 若某天想要「每文件都吃满 2.5M 的画质」，加 `ICQ_FILL_BUDGET` 开关即可（当前不做）。
