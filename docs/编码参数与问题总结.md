## 一、最初问题的根源（2 版为什么慢/报错，1 版却没事）

| # | 症状 | 真正原因 | 处理 |
|---|---|---|---|
| 1 | hevc/av1 都可能报 `Invalid FrameType:0.` | 用了 QSV 的 look-ahead（`-look_ahead_depth`/`-extbrc` 组合），而这台驱动在"硬件解码 + look-ahead"下会崩 | **彻底不用 look-ahead**（实测 ICQ 下它本来就无效） |
| 2 | 不报错也极慢，CPU 解码只有 0.x 倍速 | 崩掉后回退 CPU 解码重试 → 变成 ≈0 帧永久挂起（看起来"在编码"其实没进度） | 加 **out_time 看门狗**：超时即终止；并把"编码器侧错误"与"解码器侧错误"分开，前者不再触发解码回退 |
| 3 | 音频报 `Quality-based encoding not supported`（exit -22） | `-global_quality` 未限定作用域，漏给了音频编码器 | 改成 **`-global_quality:v`** |
| 4 | 视频 TargetUsage 变成 7、"Invalid compression level" | `-compression_level 10` 是音频参数，漏给了视频编码器 | 改成 **`-compression_level:a`** |
| 5 | 偶发 `Error creating a MFX session: -9` | 进程被强杀后 QSV 会话没释放 | 改成**先 terminate 再 kill** |
| 6 | 编完却一直不结束 | stdout EOF 哨兵只消费一次 | EOF 后**显式 wait()** |
| 7 | 误报"超上限" | 比较时一边是 bit/s、一边是 kbps | 统一单位 |
| 8 | 明明有硬解却报"无硬件解码" | 能力探测取了 `videos[0]`，可能命中的是音频/损坏文件 | 先分类候选文件，再用**第一个真实视频**探测 |

**结论**：1 版之所以没事，是因为它没有这些"自动回退/自动探测"逻辑——2 版的慢和报错全部来自这些新增逻辑的边角情况，而非硬件或驱动不行。

## 二、QSV ICQ 的真相（跨 8 个构建实测）

**ICQ（官方推荐的质量模式）能否启用，取决于 ffmpeg 构建，与显卡驱动无关。**

| 构建 | `-global_quality:v 30` 的结果 |
|---|---|
| ffmpeg **9.0.2 发布版**、**9.0 分支（n9.0.2-22）** | ✅ `RateControlMethod: ICQ / ICQQuality=30` |
| ffmpeg 8.0 发布版、2025-04 / 06 / 08 各 git 构建 | ✅ ICQ |
| **2026-10 的 master 构建**（N-127054、gyan 2026-10-01 full） | ❌ 参数送不到编码器，落到 "CQP by default"（QP 是出厂默认 20/26/33） |

- 两者用的是**同一个 oneVPL 运行时**（日志都是一样的 `Use Intel(R) oneVPL ... version 1.1`）→ **换驱动解决不了**。
- master 上逐项验证：`-preset`（私有）、`-g`、`-bf`、`-b:v`、`-q:v` **全部正常送达**，**只有 `-global_quality` 送不到**。
- 编码器源码里 ICQ 分支仍然存在，9.0 分支正在正常使用 → **不是 ICQ 被废弃**。
- Changelog 里 **7.0 明确写过** "Change the default bitrate control method from VBR to CQP for QSV encoders" → "默认 CQP"是**有意为之**，但不影响 ICQ 可用性。
- 推断（未从源码确证）：master 似乎在把质量选项统一到 `-q`/`qscale` 通路，而 qsvenc 把 QSCALE 解释成 CQP，于是 ICQ 入口被旁路。

**处置**：PATH 换成 9.0 分支构建；脚本另加"自动找支持 ICQ 的 ffmpeg 并询问切换"兜底。
**注意**：AV1 的 ICQ 同样只在 9.0 分支/发布版可用；它的 CQP(`-q:v`) 标尺失真（q40 仍要 7 Mbps 以上，压不下体积）。

## 三、参数实测结论（这些都带数据）

### 3.1 效率优先级（同画质比码率）

| 优化项 | 省多少 | 什么时候有效 |
|---|---|---|
| **ICQ 取代 CQP(`-q:v`)** | **约 5~7%** | 质量模式（默认路径）—— 最大的一笔 |
| **GOP 拉长**（见 3.2） | 4.1%（8 秒）/ 7.5%（33 秒） | 两种模式都有效 |
| **extbrc** | **约 3.7%** | **只在上限(VBR)模式有效**；ICQ 下 0% |
| preset veryslow（vs medium） | 2.6% | 都有效 |
| GOP 20 秒 vs 10 秒 | 1.8% | 两种模式 |
| 上限 VBR vs ICQ（同码率） | ICQ 高约 0.4 VMAF，且**最差画面差距巨大**（min VMAF ≈75 vs ≈54） | 上限是"体积可控"的代价 |

### 3.2 GOP：整片实测（55.8s 录屏，ICQ q32，全片平均码率）

| GOP | 码率 | 相对 |
|---|---|---|
| 4.2s | 2008 kbps | — |
| **8.3s（采用）** | **1926 kbps** | **-4.1%** |
| 16.7s | 1882 kbps | -6.3% |
| 33s | 1857 kbps | -7.5% |
| 50s | 1862 kbps | -7.3% |

→ 拐点 ≈30 秒，**取 8 秒**：拿到约一半收益，关键帧间隔仍短（拖动定位、硬件播放器兼容性好）。
（同样实测 720p 素材：4.2s→16.7s 只省 2.1%，趋势相同幅度更小。）
**注意**：20 秒片段看不出 GOP 效果（一段里最多 1~2 个 I 帧），必须整片测——这点踩过坑。

### 3.3 为什么那些 QSV "额外优化参数"全都没用

**ICQ 是恒定质量模式，没有码率目标，所以所有"码率控制类"参数都无处发力：**

| 参数 | 本来管什么 | ICQ 下为什么无效 |
|---|---|---|
| `-extbrc` | 扩展码率控制 | 只在 CBR/VBR/QVBR 下运行 |
| `-look_ahead_depth` | 前瞻分配码率 | 官方说明"extbrc 开启时可用"，而 extbrc 本身要码率模式 |
| `-mbbrc` | 宏块级码率控制 | 需要码率控制；实测反而更差 |
| `-adaptive_i/-adaptive_b/-b_strategy` | 按码率决定 I/B 帧布局 | 跟着码率控制走 |
| `-scenario archive` | 场景提示 | 实测输出**逐字节相同** |
| `-rdo 1` | 率失真优化开关 | 驱动已用内部默认，实测无变化 |
| `-low_power 0` | 选 PAK 还是 VDENC 通路 | 影响**速度**不影响"每比特画质" |
| `-p_strategy 2` | P 金字塔 | 官方要求 `-bf 0`，实测**直接编码失败** |

**ICQ 下真正有用的只有三个：质量值（QP）、`-preset`(TargetUsage)、GOP 长度。**

### 3.4 HEVC vs AV1（都用 ICQ，两段素材，分段线性插值）

| 素材 | 共同 VMAF 区间 | 中点处码率 | 结论 |
|---|---|---|---|
| 1290x2796@60 录屏 | 83.2~88.4 | HEVC 2203 vs AV1 2545 | **HEVC 省 13.4%** |
| 720p 素材 | 68.9~76.7 | HEVC 410 vs AV1 482 | **HEVC 省 14.9%** |

用**对 AV1 更友好的 NEG 模型**（`vmaf_v0.6.1neg`）复测，方向一致（HEVC 仍领先），排除了"VMAF 偏袒 HEVC"的疑虑。
→ 你这个用途（1080p+ 归档、1~3 Mbps 档）**选 HEVC 是对的**；AV1 的硬件编码器在 Arc 上单位码率效率不如它的 HEVC。

### 3.5 上限模式最佳配置（1500k 目标，录屏片段）

| 配置 | 码率 | VMAF | min |
|---|---|---|---|
| g500 无 extbrc | 1469 | 82.24 | 52.97 |
| g500 +extbrc | 1415 | 82.56 | 53.12 |
| **g1000 +extbrc** | **1401** | **82.67** | 52.95 |
| g1000 无 extbrc | 1455 | 82.57 | 53.18 |

### 3.6 D3D12VA（复测后不采用）

- 可用但**必须显式**：`-init_hw_device d3d12va=hd -i IN -filter_hw_device hd -vf format=nv12,hwupload -c:v hevc_d3d12va`
- 同画质比 QSV 多约 **30~40% 码率**（且无 preset/TargetUsage 可调）
- **QVBR 在此驱动上失效**：`-qp 30` 与 `-qp 38` 输出逐字节相同，且无视 `-b:v/-maxrate`
- `av1_d3d12va` 直接失败
→ **结论：用 QSV + veryslow + ICQ。**

### 3.7 构建之间没有性能差异

新构建（9.0 分支）与 2025-08 构建，**同参数下码率/VMAF 基本相同（±2%）**。
之前一度看到"差 27%"，是"整片 vs 20 秒片段"的 GOP 效应造成的错觉，不是构建差异。

## 四、最终定稿参数

```
Intel QSV —— 质量模式（默认）
  -c:v hevc_qsv -preset veryslow -global_quality:v <26~38> -g <8秒 × 该文件帧率>

Intel QSV —— 上限模式（只给超标的文件兜底）
  -c:v hevc_qsv -preset veryslow -b:v <CAP>k -maxrate <1.2CAP>k -bufsize <2.4CAP>k -extbrc 1 -g <8秒 × 该文件帧率>

解码：QSV 零拷贝硬解 → D3D11VA → CPU（自动探测）
音频：Opus VBR（源已是 Opus 且不超目标 1.25 倍则直接复制）
永不使用：look-ahead 系列（ICQ 下无效、码率模式下会崩）
```

GOP 是**按每个文件自己的帧率**分别换算的（实测：59.99fps→480 帧、22.00fps→176 帧、VFR 16.41fps→131 帧）。

**NVENC 参考（待你机器实测确认）**：
```
-preset p7 -tune uhq|hq -rc vbr -cq <Q> -b:v 0 -multipass fullres -rc-lookahead 32
-spatial-aq 1 -temporal-aq 1 -aq-strength 8 -bf 4 -b_ref_mode middle -g 240
上限时只加 -maxrate/-bufsize（CQ 目标不会被天花板破坏）
注意：AV1 的 CQ 是 0~255、HEVC 是 0~51；9.0 分支里上述选项全部存在
```

### 第九轮做的流程精简

**删掉的步骤**（都是"等待多、信息杂"的部分）：
- 本机能力实测的展示（保留 1 秒静默自检，界面不再显示）

- 汇总里的压缩倍数（只保留 `-x%`）

**改成瞬间决策**：码率上限不再靠"采样 4 段 ×30 秒"判断，而是用
`源码率 ÷ 5 ≈ ICQ 产出码率`（实测比例约 1/4~1/6）直接判断该文件走质量模式还是上限模式——不解码、不采样、零等待。
万一估错，`run_ffmpeg` 会在编码完成后实测成品码率，**超过上限就用上限模式自动重编该文件**（实测：故意判错时 2.5 Mbps → 自动重编 → 1391 kbps ✓）。

**默认值变化**：质量 Q32 → **Q30**；上限 不限制 → **1.5 Mbps**；音频 48k → **64k**。

**关于观感**（用户实测反馈，与 VMAF 结论不完全一致，记录备查）：
录屏压到 1.5 Mbps 时用户更偏好 **HEVC**；而低码率 **AV1** 噪点更少、涂抹感更强、细节更少但观感更"干净"。
VMAF 在这类素材上偏向 HEVC，所以"指标最优"与"观感最优"可能不同——默认取 HEVC 1.5 Mbps。

## 七、同码率对比 AV1 vs HEVC（硬件）与软件 SVT-AV1（追加实测）

测试条件：capped VBR（`-b:v` + `-maxrate 1.2×` + `-bufsize 2.4×` + `-extbrc 1`）`-preset veryslow`；
AV1 在 VBR 下实际码率普遍比目标高 7~15%，因此**统一换算到同一实际码率**再比较。

### 7.1 硬件 QSV：HEVC vs AV1（同实际码率，VMAF/XPSNR）

| 实际码率 | iPhone 录屏 1290x2796@60（源 15 Mbps） | 720p 素材（源 1.8 Mbps） |
|---|---|---|
| 400k | **AV1 66.3** vs HEVC 59.5（AV1 大胜 +6.8） | HEVC 72.9 vs AV1 72.3（HEVC 略胜） |
| 600k | AV1 71.9 vs HEVC 70.5 | HEVC 75.4 vs AV1 74.5 |
| 800k | AV1 76.1 vs HEVC 75.4 | HEVC 76.6 vs AV1 76.0 |
| 1000k | HEVC 78.6 vs AV1 78.3（**交叉点 ≈1 Mbps**） | — |
| 1200k | HEVC 80.8 vs AV1 80.4 | — |

**结论**：Arc 的硬件 AV1 只在"**高分辨率 + 极低码率（<1 Mbps）**"有优势（400k 时领先 6.8 分）；
1 Mbps 以上 HEVC 反超；对已经压过的 720p 素材，HEVC 全程略胜。
注意与"质量模式（ICQ）下 HEVC 省 13~15%"并不矛盾——那是恒定质量模式，AV1 的 ICQ 实现较弱，而它的 VBR 模式相对正常。

### 7.2 真正的赢家：软件 SVT-AV1（preset 6）

| 指标 | iPhone 录屏 | 720p 素材 |
|---|---|---|
| 同码率 400k | SVT VMAF 76.0 vs QSV AV1 66.3 vs HEVC 59.5 | SVT 74.3 vs HEVC 72.9 vs AV1 72.3 |
| 同码率 800k | SVT 82.0 vs QSV AV1 76.1 vs HEVC 75.4 | SVT 76.7 vs HEVC 76.6 |
| 同码率 1200k | SVT 84.4 vs QSV AV1 80.6 vs HEVC 80.8 | — |

**同画质所需码率（越低越省）**：

| 目标 VMAF | HEVC(QSV) | AV1(QSV) | **SVT-AV1** | SVT 相对最省 |
|---|---|---|---|---|
| 70 | 590 kbps | 550 kbps | **410 kbps** | 省 25~31% |
| 75 | 780 | 750 | **410** | 省 45~47% |
| 80 | 1100 | 1170 | **610** | 省 45~48% |
| 82 | 1360 | 1440 | **810** | 省 40~44% |

→ **同画质下软件 SVT-AV1 比两个硬件编码器省 40~48% 体积。**
速度（i3-12100F，preset 6，1290x2796@60）：15 秒素材约 23~30 秒 ≈ **0.5~0.65× 实时**；720p 素材约 3× 实时。
更慢的 preset（4 / 2）画质还会更好。
**代价**：AV1 在老设备/老播放器上兼容性不如 HEVC。

### 7.3 画质评估方法横向比较

| 方法 | 本构建是否可用 | 评价 |
|---|---|---|
| VMAF v0.6.1（默认） | ✅ | 经典；对 AV1 有轻微偏见 |
| **VMAF NEG v0.6.1** | ✅ | **跨编码器比较的推荐模型**（去掉"增强增益"项） |
| **XPSNR（2023）** | ✅ | **最值得加的"新方法"**：感知加权、比 VMAF 快约 3 倍、速度快且结论一致 |
| SSIM | ✅ | 偏老，仅作旁证 |
| VIF / vmafmotion / PSNR / msad | ✅ | 备用，本次不需要 |
| VMAF banding（vmaf_b_v0.6.3） | ❌ 本构建未打包 | 对色带敏感（录屏/动画有用） |
| Butteraugli / **SSIMULACRA2** | ❌ 需外部工具 | SSIMULACRA2（2022）是当前 SOTA 感知指标，ffmpeg 内没有 |

**实测结论：VMAF / NEG / XPSNR / SSIM 四种方法在每一个码率点上给出完全一致的排序**，
所以这次的结论不是某个指标的偏差造成的。推荐日常用 **VMAF NEG + XPSNR 交叉验证**。

## 八、追加实测：还能不能再开更多优化？（第十轮）

### 8.1 视频（HEVC QSV）：在**当前默认的 capped VBR 1500k** 下逐个试，结论是"已经没有可挖的了"

基准 B0：`-preset veryslow -b:v 1500k -maxrate 1800k -bufsize 3600k -extbrc 1 -g 480`
→ 1394 kbps / VMAF 82.62 / min 53.23 / 日志 `GopRefDist=8 Idr=1 NumRefFrame=4`

| 加的开关 | 结果 |
|---|---|
| `-mbbrc 1`、`-b_strategy 1 -adaptive_i 1 -adaptive_b 1`、`-scenario 3`、`-rdo 1`、`-max_frame_size_p 62500`、`-transform_skip 1` | **输出与基线逐字节相同**（驱动直接忽略） |
| `-max_qp_p 45 -max_qp_b 45` | 82.65（+0.03）→ 无意义 |
| `-gpb 0` | 82.46（**-0.16**）→ 保持默认 |
| `-dblk_idc 1` | 82.37（**-0.25**）→ 不用 |
| `-idr_interval 4` | 码率 -3.1%，但 VMAF **-1.10** → 效率更差 |
| `-bf 4` / `-bf 8` | 码率 +6.6%/+3.9%，VMAF -0.73/-0.66 → 更差（保持默认，日志显示默认 GopRefDist=8） |
| `-bf 0` | **编码失败** |
| **`-low_delay_brc 1`** | **灾难：35 kbps / VMAF 0**，绝不能用 |
| ICQ 模式下 `-mbbrc 1` | 422k(-8.7%) 但 VMAF -1.37 → 更差 |
| ICQ 模式下 `-idr_interval 4` | 459k(-0.6%)，VMAF +0.06、min +0.56 → 在噪声范围内，不采用 |

**`-qsv_params` 语法探测**（可触达 ffmpeg 未暴露的 MFX 参数）：
- ✅ 裸字段名可用：`-qsv_params "NumRefFrame=8"`（日志确认 `NumRefFrame: 8`）
- ❌ `mfx.NumRefFrame=8`、`mfx.Encode.NumRefFrame=8`、`Denoise=1`、`BRefType=1` → 直接失败（说明该编码器结构里没有 Denoise/BRefType 这些字段）
- `NumRefFrame` 实测**没有收益**：8 → 输出与基线逐字节相同；16 → +0.04 VMAF；**2 → VMAF 暴跌 7.6 分**（参考帧少了会显著变差）

→ **结论：当前参数集已经是这套硬件/驱动能暴露的极限**。19 个额外开关里没有一个能提升"同码率画质"。

### 8.2 音频（Opus）：当前设置已是最优，指标用 SI-SDR（尺度不变，越高越好）

同一实际码率（CBR 64k）下比较帧长：

| frame_duration | 实际码率 | SI-SDR |
|---|---|---|
| **60 ms（当前）** | **65.3 kbps** | **19.61 dB** |
| 40 ms | 65.7 | 19.61 |
| 20 ms（libopus 默认） | 67.1 | 19.62 |
| 10 ms | 69.1 | 17.83 |
| 5 ms | 73.9 | 16.79 |

→ 60/40/20 ms 画质相同，但 **60 ms 所需码率最低**；10/5 ms 明显更差。当前用 60 ms 是对的。

复杂度（CBR 64k，60ms）：`cplx10 = 19.61 dB` > `cplx5 = 19.35` > `cplx0 = 19.31`
→ **compression_level 10 确实有收益**（同码率 +0.3 dB），保持。

VBR vs constrained/CBR：VBR 56.1 kbps 得 18.69 dB；constrained 要 65.2 kbps 才到 19.62 dB
→ 换算到同画质，**VBR 约省 8% 码率**，保持 `-vbr:a on`。

码率档位的质量增长（VBR 60ms cplx10）：

| 目标 | 实际 | SI-SDR |
|---|---|---|
| 40k | 37.2 | 14.35 dB |
| 48k | 44.3 | 15.42 dB |
| **64k** | **56.1** | **18.69 dB** |
| 96k | 76.4 | 21.80 dB |

→ 48k → 64k 是**陡坡**（+12 kbps 换 +3.3 dB），所以 64k 是性价比拐点，默认 64k 合理（删掉 32k 是对的）。

**结论：音频能开的优化项（帧长 60ms、复杂度 10、VBR on、application=audio）都已经在用了**；
`-fec` / `-dtx` / `-packet_loss` / `-mapping_family` 是给"网络丢包/实时传输"用的，做归档文件没有意义。

## 十五、并发收益实测（新增 --concurrency-test）与 v7

用法：`python UniversalEncoder_v7.py --concurrency-test`（目录里放一个视频即可）
做法：同一片段分别用 1/2/3/4 路并行编码，量**合计吞吐**与**单文件速度**。

本机 Intel Arc A380 实测（1290x2796@60 录屏，10 秒片段，上限模式 1500k）：

| 路数 | 总耗时 | 合计吞吐 | 相对 1 路 | 单文件速度 |
|---|---|---|---|---|
| 1 | 4.6s | 2.18x | +0% | 2.18x |
| **2** | 5.2s | **3.82x** | **+75%** | 1.92x |
| 3 | 7.6s | 3.96x | +81% | 1.48x |
| 4 | 10.0s | 3.99x | +83% | 1.01x |

**结论：2 路是拐点**——拿走 75% 的吞吐收益，单文件速度只掉 12%；
3 路起总吞吐几乎不涨（+6%/+3%）但单文件速度继续掉（1.48x→1.01x）。
所以 v7 把 `INTEL_MAX_WORKERS` 定为 **2**（N 卡仍按引擎数自动，单引擎=1）。

判定规则：`BENCH_MIN_GAIN = 0.10`（再加一路的总吞吐增益不足 10% 就不加）。
换机器/换显卡后重跑一次 `--concurrency-test` 即可得到该机的最优路数。

这正是需要「自适应」的理由：换素材/换机器时它会重新给出该场景下的最优值。

## 十七、并发路数默认自适应（v9）

结论：**不再需要手工判断素材是 720p 还是 4K**，脚本自己测。

- `AUTO_WORKERS = True`（默认）：首次运行在**本批最重的那个文件**上短测 1/2/3 路，
  按「再加一路吞吐增益不足 10% 就不加」选路数；不足阈值会**立即停止后续测量**（省时间）。
  结果缓存 `_workers.json`，之后每次直接用；换显卡/驱动/ffmpeg 版本会自动重测。
- `AUTO_WORKERS = False`：退回固定 `DEFAULT_WORKERS = 2`（实测失败时也用它兜底）。
- `--concurrency-test`：手动跑完整对照表（1~4 路），只打印不改配置。

为什么样本取最重的文件：用轻松的小文件测会得出偏高的路数，遇到重素材反而拖慢单文件速度；
取最重的那个更保守、更接近最坏情况。

本机实测（Intel，批次里含 720p 与 1290x2796@60 两种素材）：
首次运行 32 秒完成实测并选中 **2 路**（最重文件得出的保守值），第二次运行 16 秒（缓存命中，不再实测）。

### 3. 容差为何保持 1.08、为何不吃满预算




被上限接管的 4 个文件最终落点：2.62 / 2.40 / 2.50 / 2.33 Mb/s → **均值 2.46 = 上限的 98.5%**，即「总码率稳在 2.5 左右」已经实现。容差只是验收阀门（结果 ≤2.7 不再压第二遍），不改变反解目标（2.5M）；提高容差会让落点漂向 2.7~2.8，反而破坏可预测性。


Q 是整数、一格约 7~13% 码率 → 无法精确落在 2.5M，只能在 2.3~2.7 的带里取，这是可预测性的物理边界。


不吃满预算（不对简单文件继续降 Q 顶到上限）：那会把上限（天花板）变成目标，体积上涨、且画质不再可比。


### 4. 为何「同画质可量化」成立




- 画质导向：12/16 文件直接 Q32 过关 → 画质完全一致，可横向比较；
- 4/16 硬素材被抬到 Q33~Q40 → 体积封在 ~2.5M，这部分画质低于 Q32（2.5M 上限的代价）；
- 两者互补、不可兼得：吃满体积就无法同画质，要同画质就得放弃对硬素材的体积封顶。


### 5. 关键实测结论（勿忘）




- 同 Q 数字在不同版本含义不同：CQP(-q:v) 与 ICQ(-global_quality:v) 差别巨大（1080p Q32：352 kbps / VMAF 78.3 vs 621 kbps / 85.9）；medium 与 veryslow 几乎无差（621/85.90 vs 629/85.92）。ICQ 相对 CQP 的同码率优势只有约 +0.6 分；之前说的 +4.9 分是 ICQ 对比 VBR 硬封。
- 源码率 ≠ 内容难度：同一 Q32，静态 UI 只出 0.56~1.5 Mbps，屏内视频/游戏/噪点出 2.5~6 Mbps；1080p22 与 1290p60 像素率差 4.6 倍，是同 Q 码率基线差异的主因。
- 启动：4.9s → 1.8s（合并进程）→ 1.6s（缓存）→ 0.1s（平台判断改看编码器列表）。根因：前几版补丁误打到 benchmark_concurrency() 里的同名调用。


### 6. 遗留事项




1. **NVIDIA QVBR 需在 N 机验证**：上限模式已改为 -b:v <上限> + -maxrate/-bufsize（v36，build_ffmpeg_command 约 3292 行起），并跳过 ICQ 反解（一遍完成）。需确认：①是否咬住 ~2500 kbps；②与 -cq 同用时画质是否变差（不对就把该行改回 -b:v 0）。
2. N 卡可用 -rc-lookahead / -lookahead_level（安全），本机无卡未加。
3. 菜单【9】【10】的现场实测分支未验证；【9】实测在简单素材上会挑 veryslow（测出过 VMAF 19.88 这类垃圾值），建议用默认档位（1）。
4. NVENC 分支上方仍有一句过时注释（称 CQ 模式平均码率必须为 0），仅注释。
5. 旧 VBR 兜底（1.05）已加 not ICQ_CAP_MODE，不再与 ICQ 反解打架。

## 二十三、杜比视界保留（v47~v49，已实测通过）




### 1. 实测结果




源 `IMG_6354.MOV`：hevc **Main 10** · 1920x1080@30 · bt2020/**arib-std-b67(HLG)** · side_data=**DOVI configuration record** · 232 帧 · 7.73 秒 · 8.02 MB


输出 `IMG_6354.mp4`：**8.02 MB → 1.27 MB（−84%）**，探针：


```
profile=Main 10 | pix_fmt=yuv420p10le | color_transfer=arib-std-b67
codec_tag_string=hvc1 | side_data_type=DOVI configuration record
```
即：**压完仍然是杜比视界**。


### 2. 实现（6 步，菜单【13】自动模式）




1. ffprobe 探测：`side_data_type` 含 DOVI（或 tag 为 dvh1/dvhe）
2. **源不能直接喂 dovi_tool（它不认 MOV/MP4）** → 先 `hevc_mp4toannexb` 提 ES → `dovi_tool extract-rpu`
3. 10bit HLG 编码（零拷贝 QSV）
4. 编码结果提 ES → `dovi_tool inject-rpu`
5. 重封装：`-tag:v hvc1 -strict unofficial`（hvc1 而非 dvh1，符合 Apple 对 8.4 的惯例）
6. **移植 `dvvC` 配置盒**：源的盒插到输出 `hvcC` 之后，并把祖先盒 size 各 +N；sample entry 改名 hvc1


任一步失败 → 保留 HLG 产物 + 日志写明，不影响整批。`dovi_tool` 从脚本目录 → PATH 查找。


### 3. 三个坑（都已解决）




| 坑 | 现象 | 解法 |
|---|---|---|
| dovi_tool 不支持容器 | `Error: Invalid input file type` | 先提 ES 再处理 |
| 零拷贝 + `-pix_fmt p010le` 冲突 | hevc_qsv 报 `-22 Invalid argument`、0 字节输出 | 零拷贝时**不要**指定 `-pix_fmt`（8bit 源强制转 10bit 亦然） |
| 祖先盒按类型路径判断 | 音频轨盒子被一起改坏（`missing mandatory atoms`） | 必须按**偏移包含关系**判断祖先盒 |


### 4. 限制




- **仅「安全模式（output/）」支持 DV 保留**：原地替换是先换源文件，后处理再跑时源已是 HLG。
- 丢的是 DV 的**逐场景动态元数据**吗？不——本方案用 `inject-rpu` **把原 RPU 注回**，并移植 `dvvC` 盒，所以 DV 是**真正保留**的（探针可见 DOVI 记录）。
- 前提约束：编码**不能 trim、不能改帧率、不能丢帧**（RPU 与帧一一对应），我们的流程本来就不做这些。


### 5. 4K 素材的位深/块状问题（结论）




- 实测 4K 输出 `Top-student.mp4`：3840x2160 · 8bit · bt709 · **2.29 Mbps** → **bpp 0.0092**（自然影像需 0.02~0.03）→ 放大见块状是**码率/量化问题**，不是位深问题。
- **强制把 8bit 源编成 10bit 不可行**（QSV 上 EINVAL；即使换滤波链也要慢 ~40%，且本批素材色带指标为 0）→ 已放弃该功能。
- 正确解法：4K 用【7 上限】**5.0~5.5 Mbps** + 【12 质量地板】**Q36**。

## 二十四、杜比视界：结论（v50~v57）

### 1. 最终建议：**默认输出 HLG（【13】= 关）**

iPhone 杜比视界 = **profile 8.4（HLG 基底 + DV 动态元数据 RPU）**。4K60 实测（IMG_6430）：

| 方案 | 基底层与源之差 | 苹果设备实际观感 | 体积 |
|---|---|---|---|
| **HLG（推荐）** | **+0.7%** ✓ | **忠实**（无额外加工） | 最优（B 帧可用） |
| 保留 DV（实验性） | ≈−0.7%，单帧最大 7.7 级波动 | **偏亮** ✗（把不匹配的 RPU 渲染上去） | **+40%** ✗ |

**结论**：重编码后复用原 RPU 属"元数据与画面对不上"。禁 B 帧只消除最剧烈的帧序错配（抽搐），
基底特性改变导致的色调偏移无法靠注入修复 —— 是路线固有缺陷，不是实现问题。

| 源 | gop1 | gop2 | gop3 | gop4 | gop8 | 1→2 | 2→4 |

## 二十七、v70~v76：参数自动化收尾与精简

### 1. 像素率兜底（v70）

### 4. 音频参数精简（v74~v76）

原：-c:a libopus -b:a <n> -vbr:a on -compression_level:a 10 -frame_duration:a 60 -application:a audio -ac <n>
现：-c:a libopus -b:a <n> -vbr:a on -ac <源声道数>

依据（ffmpeg 官方帮助实测打印）：
- -vbr 默认 on、-application 默认 audio、-compression_level 默认 10 → 删
- -frame_duration 默认 20ms（原设 60ms 只省约 0.3% 且兼容性略差）→ 回到默认
- -vbr:a on 保留（用户要求：日志可见）
- -ac 保留（防止多声道把总码率摊薄到每声道）——用原 helper output_audio_channels(info)，
  立体声源输出 -ac 2；**多声道源是否为上限 2 尚未验证**（遇到时看日志）。

### 5. -forced_idr 的取舍

v60 曾加 -forced_idr 1（QSV）/-forced-idr 1（NVENC）保证闭合 GOP；
实测该 QSV 配置**本来就输出 IDR**（无此参数时关键帧也是 IDR），故 v76 按用户要求移除。
风险：换驱动/版本后若编码器改出非 IDR 关键帧，可能出现「点进度条跳回前几秒」，
一行即可加回。

### 6. 状态栏「逐行往上滑」

仅出现过一次，判断为**编码中途的日志打印与状态栏重绘相互打断**（如像素率提示、元数据补写日志）。

## 二十九、v79~v81：faststart 根治、跟手问题的最终定论与代码审计

### 1. ★ faststart（本轮最重要的修复）

**症状**：即使 GOP 设为 1 秒、无 B 帧，iOS 相册拖动仍卡；原片丝滑。

**根因**：脚本主编码（原 3809 行）本就有 `+faststart` ✓，但**两处"重新封装"步骤只写了
`+use_metadata_tags`、漏了 faststart**：
- 「元数据补写」（原 1846 行）—— 只要开了元数据保留，**每个产物都会走这一步** → `moov` 被挪回文件尾部 ✗
- 「DV 重封装」（原 1944 行）—— 同理 ✗

**修复（v79）**：两处改为 `+use_metadata_tags+faststart`。实测产物头部盒 `ftyp,moov` ✓。

**为什么影响拖动**：iOS 相册拖动时高频检索样本表（Sample Table）；`moov` 在尾部 → CoreMedia
在文件首尾反复跳读 → IO 寻址拥堵 ✗（与编码帧类型无关，故解释了"GOP=1 仍卡"）。

### 2. B 帧：最终定论（五档 × 3 源 × VMAF，参照=原片无损副本）

| 源 | default(不写-bf) | bf0 | bf1 | bf2 | bf3 | VMAF 极差 |
|---|---|---|---|---|---|---|
| 录屏 1290p60 | **2906 kbps** / 93.09 | 2765 / 92.60 | 4100 / 93.54 | 3991 / 93.52 | 3563 / 93.44 | 0.94 |
| 相机 4K60 10bit | **6094** / 70.39 | 9222 / 70.38 | 12495 / 70.73 | 11482 / 70.66 | 8448 / 70.58 | 0.35 |
| 电影 4K30 | **3247** / 33.51 | 3812 / 33.25 | 4738 / 33.39 | 4575 / 33.37 | 3864 / 33.47 | 0.26 |

控制项：各档实际关键帧间隔 **2.00~2.05 秒完全一致** ✓（证明只改了 B 帧）。
**结论**：
- **`-bf` 保持不写**（编码器默认）✓：5 个源里 **4 个体积最小**，画质在噪声内 ✓
- 显式 `-bf 0/1/2/3` 一律更费码率（最多 +41%）✗ —— QSV 的怪癖
- **B 帧只是"码率旋钮"** ✓（VMAF 极差 ≤0.94，码率差 41%）；**与跟手无关** ✓
- ⚠️ 若 VMAF 参照做成"Q14 近无损重编"、且用 hwaccel `-ss` 切片段，会出现**帧错位**导致 VMAF 荒谬（曾出现 1.35 ✗）→ 必须用**输出侧 seek + 无损参照** ✓

### 3. 跟手问题的最终定论：由编码器决定，与参数无关

CTU/编码器对照（10 秒片段，其余全同：GOP 2 秒、Q/CRF 30、+faststart、hvc1）：

| 源 | qsv（CTU64）| x265 ctu32 | x265 ctu64 |
|---|---|---|---|
| 相机 4K60 10bit | 7.23 MB / VMAF 98.84 | 4.14 MB / 97.54 | 3.46 MB / 97.66 |
| 录屏 1290p60 | 3.90 MB / 95.63 | 2.93 MB / 92.91 | 2.66 MB / 92.90 |

**主观实测（用户真机）**：x265（ctu32 与 ctu64 **无差别**）明显跟手 ✓；**QSV 依旧卡** ✗。
→ **元凶是 QSV 硬编产出的码流特征，不是 CTU、不是 GOP/B 帧/容器参数** ✓
→ **x265 与 QSV 的率失真效率相当** ✓（x265 表面"省 43%"是 CRF30 画质更低所致 ✗）
→ 想要原片级跟手只能用软编，**代价是慢 4~15 倍** ✗（用户评估后**不做**软编档 ✓）

## 三十、v82~v85：上限失效根因、MOV×Opus、输出容器与"承诺-行为"自检

### 1. v82~v84 溯源（补记，此前只有口头记录）

- **v82**：`ICQ_CAP_TOLERANCE` 由 1.08 收紧到 **1.05**（注释未同步，见 §2 的口径分歧）。
- **v83**：**上限模式静默失效的根治**。v70 引入的"像素率兜底"在 `bpp < 0.012` 时直接
  `return`（单遍出片）→ **用户选的上限根本没执行** ✗（4K60 + 2.5M 实测出片 7418 kbps ✗）。
  v83 删掉提前 return，只保留提示，仍反解压回上限 ✓：**7418 → 2490 kbps**（3 遍，81 秒）。
  教训已固化：**任何"保护性"逻辑都不得静默绕过用户显式选项**。
- **v84**：**`.MOV` 源 + Opus 失败**。原地替换的临时文件沿用了源扩展名 → `.MOV` → mov 封装器
  → `opus only supported in MP4` ✗。改为临时文件强制 `.mp4` ✓（本版进一步抽象为"容器决定扩展名"）。

### 2. 两处口径分歧（v85 定稿）

| 项 | 分歧 | 定稿 | 依据 |
|---|---|---|---|
| `ICQ_CAP_TOLERANCE` | 常量 **1.05**，注释与理由段写 **1.08** | 常量保持 **1.05**（更紧），注释改为如实描述；自检①按 **1.08** 判 | 1.05 是 v82 起实跑通过的取值（2490 kbps）；自检是"承诺线"，比执行线松一档才不会天天误报 |
| 音频 ±20% | 规格写 ±20% | **下限 −20%（降配报警）、上限 +50%（膨胀报警）** | 实测 Opus VBR 96k 目标对纯音素材产出 **116k（+21%）** → 严格 ±20% 必然误报，自检会失去意义 |

### 3. v85 新增：输出容器（【13】）

菜单：MP4（默认）/ MKV / MOV / 跟随源。容器决定四件事：

1. **输出扩展名**：安全模式 `<stem>.<ext>`；原地替换 `<stem>.<ext>`（源扩展名随之变化）。
2. **音频编码**：MOV **强制 AAC**（MOV 不支持 Opus）；MP4/MKV 仍用 Opus 96k VBR，源为 Opus
   且码率不超 `96×1.25` 时仍走 `copy`。
3. **封装参数**：只有 MP4/MOV 下发 `-movflags +faststart`；**MKV 绝不下发**
   （matroska 没有这个私有选项，传了直接 `Option movflags not found` ✗）。
4. **码流标签**：只有 MP4/MOV 下发 `-tag:v hvc1/av01`；MKV 交给它自己写 `V_MPEGH/ISO/HEVC`。

「跟随源」只跟 MP4/MKV/MOV，ts/avi/flv/webm 一律回落 MP4（避免"扩展名 ts、内容 HEVC"的假文件）。

### 4. v85 新增：目标已存在 → 「跳过」而不是「失败」

- 原地替换 + 容器变化（`a.mkv` → `a.mp4`）时，若 `a.mp4` 已存在：**跳过、不编码、不删源**，
  面板计入「跳过已有输出」，**不计失败、也不进入重试队列** ✓（旧版 `raise` → 记为失败 → 白重试 2 次 ✗）。
- 双保险：扫描阶段先判一次（省掉无意义的全片编码）；worker 内再判一次（防并发竞态）。
- 容器变化导致源文件被删时，`_encode_run.log` 会写
  `原地替换：a.mkv -> a.mp4（已删除源文件）` ✓。

### 5. v85 新增：「承诺-行为」自检 5 条（每片编完自动跑）

| # | 检查 | 判据 | 手段 |
|---|---|---|---|
| ① | 上限 | 产物视频码率 ≤ 上限 × 1.08 | ffprobe 的 stream bit_rate（缺失则总量−音频） |
| ② | 质量地板 | 实际 Q ≤ 地板 | `plan.quality`（反解后的最终 Q） |
| ③ | GOP | 关键帧间隔 ∈ [0.8, 2.6] s（仅自适应档、时长 ≥4s） | `ffprobe -skip_frame nokey` 取关键帧时间，算中位间隔 |
| ④ | 封装 | MP4/MOV 头部 moov 在 mdat 之前 | 读文件前 4 KB |
| ⑤ | 音频 | ≥ 设定 −20%，≤ 设定 +50%（copy 档跳过） | ffprobe audio bit_rate |

输出位置：`编码完成` 模块末尾一行「自检 5 项全通过」；不通过则逐条列文件名 + 原因，
同时写 `_encode_run.log`。

### 6. v85 顺带修的既有 bug

- **重试分支用错变量**：失败重试成功后，代码仍拿**上一轮的 `result`** 去补元数据/保杜比视界
  （`result` 是循环残留变量），导致重试成功的文件漏掉元数据与旋转 ✗ → 改用 `new` ✓。
- **面板版本号写死 `v81`** → 改为 `APP_VERSION` 常量（现为 `v85`）。
- **参数预览会把 `-progress pipe:1` 带进音频行**（MKV 没有 `-movflags` 做切分点）→ 改用
  `-movflags` / `-progress` 双候选切分 ✓。
- **重名保护产生 `a.mp4.mp4`** → 源容器与输出容器相同时改用 `a.copy.mp4` ✓。
