### 4.4 B 帧：定论（不要改 `-bf`）

最严谨实验（无损参照 ffv1/x265 lossless + 输出侧 seek，VMAF 以原片为参照）：

| 源 | default(不写) | bf0 | bf1 | bf2 | bf3 | VMAF 极差 |
|---|---|---|---|---|---|---|
| 录屏 | **2906 kbps** / 93.09 | 2765 / 92.60 | 4100 / 93.54 | 3991 / 93.52 | 3563 / 93.44 | **0.94** |
| 相机 4K60 | **6094** / 70.39 | 9222 / 70.38 | 12495 / 70.73 | 11482 / 70.66 | 8448 / 70.58 | **0.35** |
| 电影 4K30 | **3247** / 33.51 | 3812 / 33.25 | 4738 / 33.39 | 4575 / 33.37 | 3864 / 33.47 | **0.26** |

- 控制项：各档实际关键帧间隔 2.00~2.05 秒**完全一致** ✓（只改了 B 帧）
- **实际 B 帧**：default→3、bf0→0、bf1→1、bf2→1、bf3→2（`-bf` 是上限）
- **结论**：`-bf` **保持不写**（QSV 默认 3）→ 5 源中 4 个**体积最小** ✓；显式 `-bf 0/1/2/3` 一律更费码率（最多 +41%）✗
- **B 帧只是码率旋钮，不是画质旋钮，也跟"跟手"无关** ✓

### 4.5 跟手问题的最终定论：**由编码器决定**

| 对比（同 GOP 2s / 同 Q·CRF 30 / 同 faststart）| 真机手感 | 体积 | VMAF |
|---|---|---|---|
| hevc_qsv（CTU 64）| **卡** ✗ | 7.23 MB | 98.84 |
| x265 ctu32 | **跟手** ✓ | 4.14 MB | 97.54 |
| x265 ctu64 | **跟手** ✓ | 3.46 MB | 97.66 |

- **ctu32 与 ctu64 手感无差别** ✓；画质几乎相同（VMAF 差 0.01~0.12）✓；**ctu64 小 10~20%** ✓
- **x265 与 QSV 的率失真效率相当** ✓（x265 表面"省 43%"是 CRF30 画质更低所致 ✗）
- → **跟手度取决于编码器（硬编 QSV vs 软编 x265/Apple），与 GOP/B帧/CTU/容器参数全无关**
- 用户决定：**不做软编档**（软编慢 4~15 倍：4K60 10 秒 14s → 66~75s ✗）
- 直播流那类"怎么折腾都卡"→ 用户决定**不管**

## 5. 历代 bug 与修复（务必不要重犯）

### 5.1 ★ faststart 被"重新封装"破坏（v79 修）

- 主编码原本就有 `+faststart` ✓，但**元数据补写**与 **DV 重封装**两步只写了 `+use_metadata_tags` ✗
  → 每次补写元数据都把 `moov` 挪回文件尾部 ✗ → iOS 相册拖动时反复跳读文件头尾 → 卡顿 ✗
- 修复：两处改为 `+use_metadata_tags+faststart` ✓（现三处路径都带 faststart ✓）
- 当前 `moov` 是前置的吗？→ 用 `产物前 64 字节含 'moov'` 判断 ✓

### 5.2 上限模式失效（v70 引入 / v83 修）★ 语义漏洞典型

- v70 加"像素率兜底"：`bpp < 0.012` 时**直接 return**（单遍出片）✗ → **上限完全没执行** ✗
  （4K60 + 2.5M → 出片 7418 kbps ✗ 而不是 2.5 Mbps ✗）
- v83：删掉提前 return，只保留提示 → 仍反解压向上限 ✓ 实测 **7418 → 2490 kbps**（3 遍，81 秒）✓
- **教训**：**任何"保护性"逻辑都不能静默绕过用户显式选项** ✗

### 5.3 `.MOV` + Opus 失败（v84 修）

- 原地替换的**临时文件名沿用了源扩展名** ✗ → `.MOV` → mov 封装器 → `opus only supported in MP4` ✗
- 修复：临时文件强制 `.mp4`（`stem + ".temp." + "mp4"`）✓ 实测成功 ✓

### 5.4 v68 事故：不设 `-g` = 250 帧

- 曾把"自适应 GOP"实现成**不下发 `-g`** ✗ → 编码器默认 250 帧（60fps ≈4 秒）→ 全片拖动卡成 PPT ✗
- **关键帧间隔必须显式给出** ✓

### 5.5 v78 事故：`print(x, flush=True)` 自动转换

- 把 `print(msg, flush=True)` 批量改成 `_run_log(str(msg, flush=True))` ✗ → `str()` 无 flush 参数
  → 每个文件执行前抛异常，被重试机制接住成"失败→重试"刷屏 ✗
- **编译检查发现不了**（运行时错误）→ 教训：自动转换必须逐参数核对或用 AST

### 5.6 其他已修

- 长正则替换菜单块时**误删函数**（`ask_gop` 等）✗ → 编译能过 ✗，只有实跑报 NameError

## 7. 杜比视界（结论：默认关，输出 HLG）

- iPhone DV = **profile 8.4（HLG 基底 + RPU）**；重编码后复用原 RPU = 元数据与画面不匹配
- 实测：**HLG 基底与源差 +0.7%** ✓；**DV 产物偏亮**（−0.7%，单帧最大 7.7 级）✗ 且**体积 +40%** ✗
- 因此【13 杜比视界】默认**关**（输出 HLG ✓ 亮度忠实 ✓ 体积最优 ✓）
- 选"保留"时的可用做法（仍实验性）：`dovi_tool` 提取/注入 RPU + 盒结构手术 + `-bf 0` + main10
- **DV 路径必须按平台取编码器**（`PLATFORM_STATE`）✓，N 卡用 `hevc_nvenc` ✓
- 元数据保留实测 8 项：creation_time、creationdate、location.ISO6709、accuracy、playback-intent、make、model、software ✓
  **无法保留**：Apple `mebx` 定时元数据轨（相机/镜头信息）✗（ffmpeg 不支持复制）
  **VFR 保留** ✓（实测 avg≈58.95 与源一致）；**旋转** ✓（`-display_rotation:v:0`，输入侧选项）

## 9. 工作纪律（这是血泪总结，务必遵守）

1. **改代码前先读真实代码**；锚点要么用精确字符串，要么从唯一字符串反向定位。**永远不要凭记忆写锚点。**
2. **写盘前三校验**：`compile()` + 关键函数存在性 + 文件字节数未异常缩短。（已拦下 4+ 次事故）
3. **PowerShell here-string 不能安全传 Python 代码**（会吃引号 ✗）→ 一律**写 .py 文件再运行**。
4. 批量改 `print(...)` 之类调用必须逐参数核对；`compile` 只能防语法，防不了运行时 TypeError。
5. 往**多行 f-string 的 print 中间**插入语句 = 语法错误 ✗ → 要么追加独立语句，要么加 f-string 片段。
6. **只有端到端实跑才算验证**；静态检查无法发现语义漏洞（v70 上限失效就是这样漏掉的）。
7. 破坏性操作（删除/覆盖）：**先 dry-run 出计划 → 用户确认 → 备份 → 执行 → 写日志**。
8. 涉及"用户显式选项"的任何分支，**不得静默绕过**；可以提示、可以降级，但不能让选项失效。
9. 实测数据要**留存成文件**（本项目的 `GOP测试\_码率汇总.md`、`B帧VMAF4\_结论.md` 等），别只存在于对话里。
10. 交付前把关键结论同步进 `编码参数与问题总结.md`，并（网络允许时）推仓库。

会被当成**输入源再压一遍**。面板上看起来像「一边说跳过、一边又压了」。

如要改：在扫描阶段把"被跳过源的目标文件"记进一个集合，扫到它时也跳过，
理由写「它是上面某个文件的已有产物」。**改动很小，但会改变"哪些文件会被压"的语义，
需用户先确认后再动。**

### 20.1 GOP 帧数下限：**保持 48 帧，不改**

| 项 | 内容 |
|---|---|
| 现象 | `calculate_gop()` 把帧数夹到最少 48 帧 → 30fps 素材请求"自适应 1 秒"实际是 48 帧 = **1.6 秒**，与面板文案"1 秒"不符 |
| 用户决定 | **不改，保持 48**（2026-11-03） |
| 技术依据 | **48 帧是 QSV 硬件的最小关键帧间隔**（实测：22fps 设 2 秒实际得 2.18 秒，属正常现象）。把下限改成 24 帧，编码器仍会抬回 48 → **改了等于白改**，只是让代码与硬件行为看起来更"整齐" |
| 现状是否影响正确性 | **不影响**。v86 起自检的 GOP 基准是 `expected_gop_seconds()`，它**把夹紧后的帧数换算回秒**再判定（30fps 自适应 → 期望 1.6 秒），所以既不会误报，面板也不会说谎 |
