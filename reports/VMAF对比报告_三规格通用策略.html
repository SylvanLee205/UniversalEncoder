一、你的三种规格，差在哪

三个素材在 ICQ Q30 下码率差近 10 倍，根因不是"内容复杂度"，而是像素率—— 每单位时间要编码的像素总量：

1290 的像素率是 1080 那个的 4.7 倍。ICQ 是恒定质量，所以它给 1290 更多码率 是"正确行为"——只是超出了你的存档预算。这就决定了：不能用同一个 Q 值套三种规格， 而要用"码率天花板"做统一约束。

二、通用策略：ICQ + 码率天花板兜底（单向）

核心原则：只在超出天花板时才上调 Q（降码率），绝不为了"花满预算"而下调 Q。
你要的是省码率，不是把每个文件都撑到 2M。所以 720p/1080p 压出来 400~700k 是正确结果， 不该被"拉高画质"去凑预算。

批量跑下来：只有 1290 这一类素材会压两遍，其余全部一遍过，额外开销接近零。

三、ICQ 迭代好弄吗？——好弄，核心就一行公式

3.1 要不要"压两次"

只有超标的文件需要第 2 遍。第 1 遍就是正常压制（用你设的 Q30/Q32）， 压完量一下视频流码率，超了才算新 Q 重压。720p/1080p 根本不会走到第 2 步。

3.2 收敛公式

实测 ln(码率) 对 Q 近似线性，斜率已标定：

Q2 = ceil( Q1 + ln(k1 / cap) / SLOPE )

SLOPE = 0.125 (HEVC)   # Q 每 +1，码率约 ×0.88
SLOPE = 0.140 (AV1)    # AV1 对 Q 更敏感

用 ceil 向上取整是刻意的——宁可多省一点，也绝不超出预算。

3.4 脚本里怎么接（3 处改动）

已写好可直接用的模块 icq_cap_patch.py，核心函数：

def icq_refit_quality(quality, measured_kbps, cap_kbps, codec="HEVC"):
    if measured_kbps <= cap_kbps:
        return quality                      # 没超预算，不动
    slope = ICQ_CAP_SLOPE.get(codec.upper(), 0.125)
    delta = math.log(measured_kbps / cap_kbps) / slope
    q2 = quality + math.ceil(delta)         # 向上取整，宁省不超
    return max(quality + 1, min(51, q2))
改动点：
  • 1顶部 from icq_cap_patch import encode_with_icq_cap + ICQ_CAP_MODE = True
  • 2build_ffmpeg_command() 的 CAPPED 分支：去掉 -b:v / -maxrate / -bufsize，只留 ICQ 的 -global_quality:v
  • 3worker 里把 ok = run_ffmpeg(cmd) 换成 encode_with_icq_cap(...)（内部自动压 1~2 遍）

详细注释和完整接入代码见 icq_cap_patch.py 文件末尾的 USAGE 段。

别用采样探测替代全片压第 1 遍。我实测过：短片（104 s 的 1290）采样 5 段 × 3 次迭代 花了 41 秒，比全片压制（21 秒）还贵一倍——瓶颈是每段一个 ffmpeg 进程的启动开销。 采样探测只在视频 > 5 分钟时才划算（1080/720 上探测只要 5~6 秒）。

五、"1290 降回 1080p20" 为什么不成立

你说内容是 1080p20fps 的抖音直播，理论上降回原生规格能省掉海量码率—— 同样的 2M，每像素比特数（bpp）能提升 4.9 倍。我实测了这条路线：

变体像素率Q码率bppVMAF
A 原生 1290p60216.4 Mpx/s392314 k0.010775.82
B 1080p60（只降分辨率）124.4362186 k0.017668.94
C 1080p3062.2342257 k0.036331.85
D 1080p2449.8332312 k0.046531.06
E 1080p20（内容原生）41.5332157 k0.052030.18
bpp 涨了 4.9 倍，VMAF 反而掉了 45 分。 我一开始怀疑是帧对齐 bug，做了 PSNR 校验排除：
60fps → 30fps → 升回 60fps（纯帧率转换，零压缩）= 33.75 dB
60fps → 24fps = 32.12 dB　·　60fps → 20fps = 31.52 dB
这说明源里有真实的 60fps 运动信息（弹幕滚动、UI 动画是 60fps 渲染的，只有视频画面本体是 20fps）。 降帧率会实实在在损失这些内容——你明确说过在意弹幕，所以这条路不通。

降分辨率同理：VMAF 掉 6.9 分，且弹幕文字会变糊。

六、最终推荐

首选：ICQ + 码率天花板兜底

# HEVC（画质优先）
ffmpeg -hwaccel qsv -hwaccel_output_format qsv -i input.mp4 \
  -map 0:v:0 -map 0:a:0 \
  -c:v hevc_qsv -preset medium -global_quality:v 30 \
  -g <fps×8> -tag:v hvc1 \
  -c:a libopus -b:a 64k -vbr on \
  -movflags +faststart out.mp4
# + 天花板 2000k：压完量码率，超了就 Q2 = ceil(Q1 + ln(k1/2000)/0.125) 重压一遍
# AV1（体积优先，比 HEVC 小约 10%，画质低 1~3 分）
  -c:v av1_qsv -preset medium -global_quality:v 30 -tag:v av01
# + 天花板：SLOPE 用 0.140

次选：AVBR（不想改架构时）

-c:v hevc_qsv -preset medium -b:v 2000k -avbr_accuracy 1000 -avbr_convergence 100

一次压制即贴合目标（实测误差 −1.4%~+1.2%），画质比 ICQ 迭代低 1.2~4.4 分， 但仍优于脚本现有的 VBR 上限模式。

不要再用的组合

  • ICQ + -maxrate/-bufsize：QSV 会静默把 ICQ 切成 CQP 并丢弃 global_quality（Q25/30/35 输出 md5 相同），CQP 又完全不限码率
  • -b:v + -look_ahead_depth：这台机器上必崩 Error encoding a frame: Invalid data
  • ICQ 下叠加保守档（关 B 帧/GPB）：码率涨 50~90%，VMAF 几乎不涨
  • ICQ 下加 extbrc / rdo / refs / adaptive_i：全是空操作（输出字节不变）
一句话总结：混批时别用同一个 Q 值——设一个码率天花板（2M）， 用 ICQ 默认 Q 压，超了就按 ceil(Q + ln(k/cap)/0.125) 重压一遍。 720p/1080p 永远只压一遍，只有 1290 这种高像素率录屏会压两遍。 嫌改脚本麻烦就用 AVBR，代价是 1~4 分 VMAF。

数据说明：VMAF 为抽样窗口均值（低/中/高运动段），1290 用时间窗口（CFR 60fps，可信）， 1080/720 用帧号窗口（这两个源是 VFR，按时间戳抽帧会错位，已改用帧号口径）。 配套脚本：icq_cap_patch.py（接入模块）、 _icq_autotune.py（采样探测版，长视频可选）、 _autotune_verify.py、_downscale_test.py。
